# Техническое задание ToyStore

## 1. Назначение системы

ToyStore — веб-приложение для продажи детских игрушек. Система предоставляет покупателю каталог товаров и позволяет оформить заказ, а администратору — управлять товарами, категориями и статусами заказов.

## 2. Роли

| Роль | Возможности |
|---|---|
| Гость | Просмотр каталога, поиск, фильтры, просмотр карточек, регистрация и вход |
| Покупатель | Всё, что доступно гостю; корзина, оформление заказа, просмотр своих заказов |
| Администратор | Управление товарами, категориями и заказами |

## 3. Функциональные требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Регистрация и вход | Пользователь создаёт аккаунт по email и паролю, входит и выходит из системы |
| FR-02 | Каталог | Система показывает список доступных игрушек с изображением, названием, ценой и остатком |
| FR-03 | Категории | Пользователь может выбрать категорию, например «Конструкторы» или «Мягкие игрушки» |
| FR-04 | Поиск | Поиск находит товары по части названия и описания без учёта регистра |
| FR-05 | Фильтрация и сортировка | Можно отфильтровать товары по категории и возрасту и отсортировать их по цене, названию и дате добавления |
| FR-06 | Карточка товара | Открывается подробная информация о товаре: описание, характеристики, цена и наличие |
| FR-07 | Корзина | Пользователь добавляет, удаляет товары и меняет количество; итог пересчитывается автоматически |
| FR-08 | Оформление заказа | Пользователь указывает контактные данные и адрес, после чего создаётся заказ |
| FR-09 | История заказов | Авторизованный пользователь видит только свои заказы и их статусы |
| FR-10 | Управление каталогом | Администратор создаёт, изменяет и удаляет товары и категории |
| FR-11 | Управление заказами | Администратор просматривает заказы и меняет их статус |
| FR-12 | Проверка остатков | Нельзя заказать товара больше, чем есть на складе |

Администраторские операции доступны только для пользователя с ролью `admin`: создание, изменение и скрытие товаров, а также создание категорий.

Администратор также видит все заказы и может менять их статус: `new`, `confirmed`, `processing`, `shipped`, `completed`, `cancelled`.

## 4. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Интерфейс работает на экранах от 360 px |
| NFR-02 | Пароли хранятся только в виде хеша |
| NFR-03 | Пользователь не может получить чужие заказы через API |
| NFR-04 | Основные API-запросы отвечают не дольше 1 секунды на тестовых данных |
| NFR-05 | Backend предоставляет OpenAPI/Swagger-документацию |
| NFR-06 | Все изменения каталога и заказов проверяются сервером |

## 5. Основные пользовательские сценарии

### Сценарий A: покупка товара

1. Гость открывает каталог.
2. Использует поиск или фильтр.
3. Открывает карточку игрушки.
4. Добавляет товар в корзину.
5. Входит или регистрируется.
6. Указывает контактные данные и адрес.
7. Подтверждает заказ.
8. Система создаёт заказ и уменьшает остаток товара.

### Сценарий B: управление каталогом

1. Администратор входит в систему.
2. Открывает раздел управления товарами.
3. Создаёт или редактирует товар.
4. Система проверяет цену, остаток и категорию.
5. Обновлённый товар появляется в каталоге.

## 6. Статусы заказа

`new` — новый заказ, `confirmed` — подтверждён, `processing` — собирается, `shipped` — передан в доставку, `completed` — завершён, `cancelled` — отменён.
